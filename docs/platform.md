# 작업 처리 서비스 설계: 규칙을 실행되는 API·워커·DB로

작성 2026-10-06. 이 문서를 먼저 커밋하고 구현한다.

## 1. 왜 만드나

이 저장소는 지금까지 처리 규칙(`fallback.py`)과 단위 검사만 담았다. 규칙이 맞는지는 보이지만, 그 규칙이 API·큐·DB·모델 호출 사이에서 실제로 지켜지는지는 보이지 않는다. 원본 팀 프로젝트(비공개)에서는 계약 검사와 통합 시험을 로컬에서 돌렸고 GitLab CI는 설정만 있고 원격 실행 기록이 없다.

이번에는 같은 규칙을 실제로 돌아가는 작은 서비스로 다시 세우고, 변경이 올라오면 정적 검사 → 단위 검사 → 계약 검사 → 컨테이너 빌드 → 장애 주입 통합 시험이 자동으로 도는 흐름을 GitHub Actions에서 실행한다. 원본 팀 코드의 사본이 아니다. 모델은 부르지 않고, 응답을 정해진 대로 돌려주는 가짜 모델 서버를 쓴다.

## 2. 구성

| 구성 | 역할 |
|---|---|
| `api` | 작품 올리기·조회·결과 확인. 올리는 즉시 원본 액자로 건다(결정 001) |
| `worker` | 큐에서 작품을 하나씩 가져와 모델을 부르고, 응답을 분류해 `fallback.apply`로 상태를 바꾼다 |
| `db` | MariaDB. 작품 상태와 시도 기록. 큐는 같은 표에서 `FOR UPDATE SKIP LOCKED`로 가져간다 |
| `model` | 가짜 모델 서버. 작품 제목에 적은 계획(`plan:timeout,ok`)대로 응답한다. 시험 전용 |

## 3. 계약

- **화면↔API.** `contracts/openapi.yaml`이 원본이다. 계약 검사는 실제 API 응답(정상·오류 모두)을 이 문서의 스키마로 검증한다. 오류 응답은 `{error, request_id}` 하나의 모양이다.
- **워커↔모델.** `contracts/model_response.schema.json`. 모델 응답은 `{"status": "ok" | "quality_below"}`만 허용한다.
- **응답 분류(워커의 경계).** 모델 호출 결과를 규칙이 아는 분류로 바꾸는 곳은 워커 한 곳이다.

| 관찰 | 분류 | 규칙 |
|---|---|---|
| 200 + 계약에 맞는 `ok` | `ok` | 결과 완성 |
| 200 + 계약에 맞는 `quality_below` | `quality_below` | 한 단계 낮춤(재시도 아님) |
| 시간 초과 | `timeout` | 같은 단계 재시도 |
| 연결 실패·503 | `engine_down` | 같은 단계 재시도 |
| 200이지만 JSON이 아니거나 계약 위반 | `invalid_response` | 같은 단계 재시도(새 분류, 결정 004) |

## 4. 관찰 가능성

- **구조화 로그.** 한 줄 JSON. API는 `request_id`(요청 헤더 `X-Request-ID`가 있으면 그 값), 워커는 `job_id`·단계·시도·분류·지연(ms)을 남긴다.
- **지표(Prometheus).** `http_requests_total{route,status}`, `jobs_total{outcome}`, `job_attempts_total{stage,classification}`, `job_retries_total`, `job_duration_seconds`. API는 `/metrics`, 워커는 9101 포트.
- **상태 확인.** `/healthz`(프로세스), `/readyz`(DB 연결).

## 5. 장애 주입 시나리오와 지켜야 할 것

| # | 주입 | 기대 |
|---|---|---|
| 1 | 없음(움직임 요청) | 결과 움직임, 원인 없음, 시도 1 |
| 2 | 품질 미달 | 입체로 낮춤, 원인 모델 낮춤 |
| 3 | 시간 초과 1회 뒤 정상 | 결과 움직임, 원인 인프라 실패, 시도 2 |
| 4 | 시간 초과 3회 | 결과 미도달, 벽에는 원본 액자, 원본 액자 외 확인 거절 |
| 5 | 계약 위반 응답 1회 뒤 정상 | 결과 움직임, 시도 기록에 `invalid_response` |
| 6 | 모델 503 3회 | 결과 미도달 |
| 7 | 처음부터 원본 액자 | 모델 호출 0회, 원인 보호자 선택 |
| 8 | DB 중지 | API는 503과 `request_id`, `/readyz` 503. DB 재시작 뒤 중지 전에 올린 작품이 끝까지 처리됨 |

모든 시나리오에서 확인하는 불변식: 결과 확인 전에는 벽에 원본 액자만 걸린다, 단계별 시도는 3회를 넘지 않는다, 결과 미도달 작품에 보호자 전환 원인이 붙지 않는다, 지표의 작업 결과 수가 DB의 작품 상태 수와 같다.

## 6. 자동 흐름(GitHub Actions)

`checks` 작업: ruff → 단위 검사(규칙·분류) → OpenAPI 문서 검증. 통과하면 `integration` 작업: 컨테이너 빌드 → `docker compose up` → 준비 대기 → 계약 검사 → 장애 주입 시험 → 실패·성공과 관계없이 로그와 지표를 실행 기록에 남긴다.

## 7. 하지 않는 것

실제 모델 호출, 인증, 여러 워커의 성능 측정, 부하 시험, 쿠버네티스 배포. 실제 사용자 트래픽은 없다.

## 8. 보호자 화면과 E2E 시험(2026-10-06 추가, 구현 전)

API 시험만으로는 보호자가 실제로 보는 상태(원본 액자 먼저, 결과 확인 전 바꿔 걸지 않음, 결과 미도달 안내)가 화면에 맞게 드러나는지 알 수 없다. 최소 화면 하나와 브라우저 E2E 시험을 붙인다.

- **화면.** `web/src/app.ts`(TypeScript, 프레임워크 없음)를 `tsc`로 컴파일해 API가 `/`에서 내준다. 작품 올리기 → 상태 표시(벽에 걸린 것·진행 상태·원인) → 결과 확인 버튼. 상태는 1초마다 다시 읽는다. API 응답 타입은 OpenAPI 계약과 같은 이름으로 선언한다.
- **E2E 시험.** Playwright(TypeScript)로 compose에 띄운 서비스를 실제 브라우저로 조작한다.
  1. 올리는 즉시 화면에 "원본 액자"가 걸리고, 결과가 나와도 확인 전에는 바뀌지 않는다.
  2. 결과 확인 버튼을 누르면 벽에 건 결과가 바뀐다.
  3. 시간 초과 3회(결과 미도달)면 안내 문구가 나오고 원본 액자 외 선택지는 비활성이다.
  4. 품질 미달이면 낮춘 결과(입체)와 그 원인이 화면에 보인다.
- **CI.** `e2e` 작업을 추가한다: compose 기동 → `npm ci` → 브라우저 설치 → Playwright 실행 → 실패 시 화면 기록(trace·스크린샷)을 실행 기록에 남긴다.
- **음성 대조.** 화면이 결과를 확인 전에 바로 걸도록 고치면 시험 1이 실패하는지 로컬에서 확인한다.
