# 005 화면 타입을 계약에서 만들고, 계약은 서버가 실제로 돌려주는 상태를 모두 적는다

작성 2026-10-11. 공개 재현에서 새로 정한 것이다(원본 팀 규칙 아님).

## 문제

- 보호자 화면(`web/src/app.ts`)의 응답 타입을 손으로 써서, 계약(`contracts/openapi.yaml`)을 바꿔도 화면 코드는 그대로 통과했다. 원인 목록에서 `guardian_switch`를 지워도 `npm run typecheck`는 종료 코드 0이었다(2026-10-11 로컬 실행).
- `GET /artworks/abc`는 FastAPI의 경로 검증 때문에 422를 돌려주는데 계약에는 200·404·503만 있었다. 통합 시험은 이 입력을 부르지 않아 드러나지 않았다. 시험의 `CHECKED` 목록은 기록만 하고 아무것도 비교하지 않았다. README의 "모든 API 응답 검증"은 실제(시험이 부른 응답만 검증)보다 넓은 말이었다.

## 선택지

| 선택지 | 판단 |
|---|---|
| 손으로 쓴 타입 유지 + 리뷰 | 어긋남을 사람이 찾아야 한다. 지금 그 방식에서 어긋남을 놓쳤다 |
| 실행 중 검증(zod 등)으로 응답 확인 | 화면 실행 때만 드러나고, 스키마를 한 벌 더 관리한다 |
| `openapi-fetch` 등 생성 클라이언트까지 도입 | 호출 3곳짜리 화면에 런타임 의존성이 생긴다. 이번 목적(어긋남 검출)에는 타입만으로 충분하다 |
| **`openapi-typescript`로 타입만 생성(개발 의존성) + CI 어긋남 검사** | 런타임 코드 변화 없음. 계약 변경이 타입 검사 또는 생성물 diff에서 실패로 드러난다 |

422에 대해서는 두 가지를 비교했다.

| 선택지 | 판단 |
|---|---|
| 서버가 정수 아닌 id를 404로 바꿔 돌려준다 | 다른 경로(`POST /artworks`, confirm)는 잘못된 입력을 422로 돌려준다. 한 경로만 다르면 화면이 오류를 다르게 다뤄야 한다 |
| **계약에 422를 적는다** | 서버 동작을 바꾸지 않고, 세 경로가 같은 규칙(잘못된 입력 = 422 `invalid_request`)을 따른다 |

## 결정

1. `npm run gen:api`(`openapi-typescript contracts/openapi.yaml -o web/src/api.gen.ts`)로 타입을 만들고 생성물을 커밋한다. `app.ts`는 `components["schemas"]`의 `Kind`·`Artwork`·`Error`를 쓴다.
2. CI `e2e` 작업에서 타입 검사 전에 `gen:api` → `git diff --exit-code web/src/api.gen.ts`를 돈다. 계약만 고치고 생성물을 다시 만들지 않으면 실패한다.
3. `GET /artworks/{id}`에 422를 적는다. id 0·음수는 404 그대로다.
4. 통합 시험에 계약 밖 입력 시험과 계약 범위 시험(검증한 상태 목록 = 계약의 상태 목록)을 넣는다. 범위 시험은 다른 시험을 모두 돈 뒤에 돌아야 하므로 파일 맨 끝에 둔다. 503은 DB 중지 시나리오(COMPOSE=1, DB 중지 중 네 경로를 모두 부른다)에서만 만들 수 있으므로, 그 시나리오를 돌리지 않을 때만 503을 범위에서 뺀다(시험 설명에 적음). CI는 COMPOSE=1로 돌아 503까지 본다.
5. README 문구는 "시험이 부른 응답을 검증하고, 계약의 모든 상태를 한 번 이상 부른다"로 고친다.

## 검사

### 2026-10-12 입력 값의 타입 검증 보완

독립 검토에서 wanted 또는 choice에 목록·객체가 오면 집합 포함 검사에서 TypeError가 발생함을 확인했다. 전체 본문의 타입 검사만으로는 필드 타입을 보장하지 못했다. 두 필드 모두 문자열인지 먼저 확인하고, 잘못된 입력은 DB 접근 전에 422 invalid_request로 반환한다. 기존 422 계약을 유지하므로 스키마 변경은 없다.

통합 시험의 계약 밖 입력 사례에 목록·객체·null·숫자·불리언을 추가한다. 실제 HTTP 상태와 오류 응답을 OpenAPI 계약에 대조하며, 유효한 입력의 작업 흐름은 기존 통합·E2E로 회귀 검사한다.

- 역검사 ①: 계약에서 enum 값 하나를 지우고 `gen:api` → `typecheck`가 실패해야 한다.
- 역검사 ②: 계약을 고치고 `gen:api` 없이 두면 `git diff --exit-code`가 실패해야 한다.
- 계약 범위: `tests/integration/test_service.py`의 `test_12`(계약 밖 입력), `test_99`(범위). Docker가 필요해 CI에서 돈다.
